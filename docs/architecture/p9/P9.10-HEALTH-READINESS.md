# P9.10 — Health / Readiness Model

Status: COMPLETE (stacked on P9.9) · Contract `observability.health-readiness@1.0.0` · Owner agent-6 · Development delegate Agent 4 · Issue #101

## Purpose

Canonical health model with **independent axes** so operators never see a generic green while critical dependencies are down. P9 reports; P3/P4/P6 policy decides.

## Axes (deep design §21)

| Axis | Question | Values |
|---|---|---|
| **LIVENESS** | Can the component process anything? | `ALIVE` \| `DEAD` |
| **READINESS** | Should this component receive new work? | `READY` \| `NOT_READY` |
| **CONDITION** | Operating guarantees | `HEALTHY` \| `DEGRADED` \| `UNAVAILABLE` |

`DEGRADED` (can operate, reduced guarantees) and `UNAVAILABLE` (cannot provide the capability) are **distinct** — tests assert they never collapse.

## Lifecycle phases

`STARTING` → `RUNNING` ⇄ `RECOVERING` → `RUNNING`

- `STARTING`: `NOT_READY` + `UNAVAILABLE` + reason `startup.in_progress`
- `markRunning()`: STARTING → RUNNING (only from STARTING)
- `beginRecovery()`: RUNNING → RECOVERING
- `completeRecovery()`: RECOVERING → RUNNING (returns post-transition report; null otherwise)

## Structured reason codes

Stable `namespace.category` vocabulary (`HEALTH_REASON_CODES`, 14 codes): `startup.*`, `liveness.*`, `readiness.*`, `condition.*`, `recovery.*`, `false_healthy.rejected`, `dependency.unknown`. Reasons may be extended with `:depId` detail (bounded list ≤ 32).

## False-healthy rejection

Critical dependency `available: false` while phase is `RUNNING` ⇒ **forced** `NOT_READY` + `UNAVAILABLE` + `false_healthy.rejected` — no path reports READY/HEALTHY under a critical outage. Optional non-critical down/degraded ⇒ `DEGRADED` + `NOT_READY` (not HEALTHY).

## Bounded, cheap queries

- Fixed dependency table (≤ 64) — `evaluate()` is O(n), pure, no I/O/clock.
- Reason list capped at 32; dependency report capped at maxDependencies.
- **Report remains available during DEGRADED/UNAVAILABLE** (full structure + stats; never fails closed to empty).
