## Four-state MCP boundary (§9 resolution)

Roadmap names `permission-required / exposed / blocked` and demands **four** declared
states. Authoritative search performed before coding:

| source | found | boundary-state? |
| --- | --- | --- |
| `P2.17-P2.26-ROADMAP.md` §P2.20 | three states only | trio confirmed |
| `manifest/ai-foundation.json#mcp` | no states (rules/concepts only) | — |
| `manifest/ai-lego-set.json#mcp-adapter` | adapter lifecycle `declared/discovered/connected/active/degraded/disconnected` | connection dimension, not exposure |
| `packages/frontend-lego/src/agents.mjs` `MCP_CONNECTION_STATES` | `connected/unavailable/permission-required/capability-unsupported` | availability dimension, not exposure |
| evidence captures (`frontend-boundary-p25.json`) | “four states, no transport” with UI mock state | not a canonical vocabulary |

No authoritative fourth **boundary** (exposure) state exists → per §9 only the
least-privileged semantic is admitted. **Canonical model (published in
`manifest/ai-foundation.json#mcp.states`, quoted by `mcp-boundary.mjs`):**

```text
declared ──permission required──► permission-required ──explicit grant──► exposed
   │                                     │                          │
   │ explicit no-authority              │ deny/expiry/invalid      │ explicit revoke
   ▼                                     ▼                          ▼
blocked ◄──────────────────────────────── blocked ◄──────────────── blocked
```

- **declared** — known as a declaration; **no authority implied**
- **permission-required** — known, not exposed until an explicit decision
- **exposed** — explicitly exposed after the permission gate passes
- **blocked** — prohibited, unknown, invalid or denied (terminal, fail-closed)

Banned names never appear as states: `trusted, authorized, available, active, allowed, connected`.

## Permission gate (§24) & authority separation (§10, §14, §17–18)

`evaluate()` walks the six canonical steps in order (proved by tests):
server declared → capability declared → supported → permission required? → explicit
grant presented? → exposed. **Any unknown/invalid → blocked.**

- Unknown server → `blocked/unknown-server` (never `permission-required` — §16)
- Unknown capability → `blocked/unknown-capability`
- Caller-claimed permission (`permission:` input) → `blocked/unknown-permission`
  (claims are never evidence; no wildcard, no inheritance — §17/§18)
- Approval satisfaction **only** via injected `ai.approval@1.0.0` `evaluate`
  (identity + scope): granted → `exposed`; pending → `permission-required/not-granted`;
  denied/expired/unknown/scope-mismatch/identity-mismatch → `blocked` with the
  stored reason. Unwired approval on a gated capability → contract-violation REJECT.
- **MCP exposure ⇏ Agent Control authority and vice versa** — the module imports only
  the foundation accessor, exposes a fixed five-function surface, and records no
  permission grants anywhere (static + behavioral tests).
- Transitions follow the quoted graph only; `blocked` is terminal (no resurrection);
  revoke/evaluate idempotent; explicit server block cascades through the guard.
