## 2. Architecture separation (§4)

Nine distinct concepts stay distinct — no `UserWithEverything`:

```text
Identity ≠ Authentication ≠ Principal ≠ Authorization ≠ Approval
        ≠ Credential ≠ Secret ≠ Session ≠ Tenant
```

Enforced structurally, not by convention: `createPrincipalSnapshot` applies an
exact key whitelist and **rejects unknown fields**. Test
`a stored user record is rejected` passes a realistic stored user record
(`email`, `firstName`, `password`, `role`, `settings`) and asserts the kernel
refuses it. A profile therefore cannot ride into the execution path even by
accident.

## 3. Security stamp semantics (§6)

```text
SecurityStamp = principalVersion + tenantVersion + policyVersion + sessionVersion
                (+ resourceVersion for a mutable resource)
```

| Presented vs current | Verdict | Reason code |
|---|---|---|
| equal | `CURRENT` | — |
| lower | `RE_EVALUATE` (`DENY` in strict mode) | `lego.version_incompatible` |
| **higher** | `DENY` | `lego.contract_violation` |

A version **ahead** of current is treated as impossible (forged or corrupt) and
denied outright rather than treated as a cache miss — nothing can present
authority the system has not issued.

**TTL is a bound, not the correctness mechanism.** `isPrincipalExpired` exists,
but the test `expiry is a bound, not the correctness mechanism` asserts an
*unexpired* snapshot can still evaluate `RE_EVALUATE`. Expiry only ever removes
entries; it never validates one. A stale stamp is never silently promoted to
ALLOW by time passing.

## 4. No new error vocabulary

`SecurityError` refuses to be constructed with any code not published in
`contracts/errors.contract.json` (reuses the P2.27 `PluginRuntimeError`
technique — foundation F16 *by construction*, not by review). The
`SECURITY_REASON` map is a **mapping onto published codes**, not a new
namespace; the test `every security reason is a published error code` iterates
it and asserts `isErrorCode` for each.

**Zero error codes were added.** The kernel reuses `auth.unauthorized`,
`auth.forbidden`, `lego.contract_violation`, `lego.version_incompatible`,
`lego.capability_unavailable` and `lego.unavailable`.

## 6. Measured benchmark (§21 — no fabricated numbers)

`node --expose-gc tools/p5/security-kernel-benchmark.mjs`
Node v20.20.2 · linux/x64 · 200,000 iterations · generated 2026-09-24T13:31:06Z

| operation | ns/op | ops/sec | heap B/op |
|---|---:|---:|---:|
| PrincipalSnapshot construction (18 permissions) | 5,279.8 | 189,401 | 6.5 |
| SecurityContext construction (single-tenant) | 2,815.8 | 355,137 | 80.3 |
| SecurityStamp comparison (CURRENT) | 857.5 | 1,166,172 | 40.1 |
| Tenant binding check (single-tenant, matching) | 325.7 | 3,070,659 | 12.9 |
| Permission lookup (hit, 18 permissions) | 44.6 | 22,411,276 | 0.1 |
| Permission lookup (miss) | 56.6 | 17,671,607 | 1.1 |
| Fail-closed rejection (malformed principal) | 8,719.4 | 114,687 | 58.1 |
| Tenant binding: multi-tenant match | 329.3 | 3,036,932 | 12.3 |
| Tenant binding: multi-tenant mismatch (deny) | 329.8 | 3,032,045 | 12.3 |

Latency distribution (ns per call):

| operation | p50 | p95 | p99 |
|---|---:|---:|---:|
| SecurityContext construction | 2,002 | 3,497 | 5,963 |
| SecurityStamp comparison | 964 | 2,028 | 2,763 |
| Tenant binding (single-tenant) | 378 | 585 | 873 |

**Honest reading of these numbers:**

- Snapshot construction (5.3 µs) is **control-path only** — once per
  authentication, never per node execution. Its cost is the SHA-256 that derives
  `permissionSetId`, which is what lets the authorization cache key on the
  permission set rather than the principal.
- The genuinely hot operations are sub-microsecond: permission lookup 45 ns,
  tenant binding 326 ns, stamp comparison 858 ns.
- `SecurityContext` construction at 2.8 µs / 80 B is the largest hot-path cost.
  It is acceptable for one construction per request but is the first place to
  look if P5.3's authorization cache shows pressure.
- **Denial is cheap** (8.7 µs worst case, and that is the *validating* path).
  This matters: if rejection were expensive, a malformed-input flood would be a
  DoS lever. It is bounded.
- **Single-tenant stays the cheapest path**: 345 ns vs 330 ns for multi-tenant
  match — the difference is inside measurement noise, so the `tenantId=default`
  promise costs nothing. It is a valid, non-penalised path.
- **No baseline-vs-P5 comparison is claimed.** There is no pre-P5 security
  kernel to compare against; these are absolute measurements of new code. A
  differential against P5.8 is recorded then.

## 8. Two gate violations found and fixed (both caused by this change)

### R9 version-incompatible — fixed correctly

```text
contract 'auth.principal' is locked at 1.0.0 but domain 'auth' declares 0.1.0
```

The domain's `contract` block did not name a primary contract, so the gate fell
back to "the domain has exactly one lock row" — which became true only because
P5.1 added the first `auth`-domain row. Fixed the same way the `auth.identity`
sub-LEGO already does it:

```json
"contract": { "id": "auth.principal", "version": "1.0.0", "tests": ["test/lego-security-kernel.test.mjs"] }
```

The vestigial `0.1.0` was never meaningful; it was simply never checked before.

### R4 internal-import — a PRE-EXISTING coupling, deliberately not papered over

Declaring `public: ["src/auth/security"]` switches on R4 boundary policing for
the `auth` domain and immediately reported:

```text
at src/auth/contract/index.mjs:32
reaches into 'src/auth.mjs', outside the public surface of 'auth'
```

This is **not** P5 code. `src/auth/contract/index.mjs` is domain
`auth.identity`, **owner agent-3**, and it re-exports `toPublicUser`/`hasOwner`
from `src/auth.mjs`. The coupling predates P5 and was invisible only because
`auth.public` was `[]`, which disables R4 for the domain entirely.

**Decision: `auth.public` stays `[]`**, matching how `node-registry`
(33 rows, 0 public), `execution` (5, 0) and `workflow` (2, 0) already operate.
The contract-lock row is the publication mechanism for `auth.principal`, which
is what R9 and `lego-boundary.test.mjs` police.

Rejected alternatives, each for a reason:

- *Publish `src/auth.mjs` too* — would re-legitimise exactly what `auth.identity`
  was created to retire (allowances A1/A2).
- *Edit `src/auth/contract/index.mjs`* — agent-3's file, out of P5.1 scope.
- *Add a new allowance* — governance debt with a `resolveBy` commitment P5.1
  cannot fulfil.
- *Change the gate* — weakening a rule to make a change pass.

The finding is recorded twice: in the `auth` domain `notes` in `domains.json`,
and as an executable assertion in
`test/lego-security-kernel.test.mjs` (`the R4 finding is recorded`). That test
also pins the reach itself, so when agent-3 retires it, publishing
`src/auth/security` becomes the natural next step.

## 10. Known limitations (no fabricated capability)

- **No authorization engine.** P5.1 defines principal/context/stamp; deciding
  `action + resource → ALLOW/DENY` against the canonical n8n scope model is
  **P5.3**. Nothing here evaluates a permission against a resource yet.
- **No session, credential, key or MFA logic.** P5.2/P5.4/P5.5/P5.6.
- **`consumers: []`** — the kernel is not yet wired into a request path. No
  behavior change to any running endpoint in this slice.
- **Permission universe is opt-in.** `permissionUniverse` must be passed to get
  unknown-scope rejection. Without it, a malformed-scope-shaped but unpublished
  permission is accepted. P5.3 should pass the canonical universe so unknown
  scopes fail closed by default.
- **`public: []`** — see §8; R4 does not police consumers of this surface yet.
- **Rust rewrite not attempted**, and not implied. If P5.3 profiling shows
  stamp comparison dominating, the candidate is `evaluateStampAuthority`
  (858 ns, pure integer comparison) — documented, not acted on.
