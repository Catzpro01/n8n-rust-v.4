# P5.2 — Session Kernel, Rotation, Revocation and CSRF: Evidence

Issue: **#215** · Parent: **#85** · Branch: `arena/p5.2-session`
Depends on: P5.1 (#214, merged `0842a05f`)

---

## 1. The defect this slice closes

The baseline session was a stateless HMAC token:

```js
signToken({ sub: user.id, iat, exp }, config.secret)
```

Unforgeable — but **unrevocable**. It asserted "I am user X" and stayed true
until it expired, so:

- **logout** only cleared the browser's cookie; every copy of the token stayed
  valid for up to 7 days;
- a **password change**, **account disable** or **"log out everywhere"** had no
  way to cut an issued session short;
- there was **no CSRF defence anywhere** in the codebase.

### The token changed shape — that is the point

```text
before   { sub, iat, exp }   bearer token: unforgeable, unrevocable
after    { sid, ver, exp }   pointer into revocable server-side state
```

The new token carries no user id, no role, no profile and no secret. Authority
lives in the record behind it and can be killed at any time.

**UPGRADE CONSEQUENCE (documented, not hidden):** pre-P5.2 tokens carry no
`sid`, so they cannot be looked up or revoked. They are therefore rejected —
every user is signed out exactly once when this lands. Refusing is the only
defensible answer for a credential the server cannot kill.

**Bounded memory under flood:** 200,000 sessions created against a store capped
at 1,000 → final size **1,000** (cap held), heap delta **55.9 KiB**.

**Honest reading.** The revocation lookup costs ~70 ns (14M ops/sec) against a
store of 10,000 sessions — that is the whole price of turning an unrevocable
token into revocable authority, and it is paid once per HTTP request, never per
node execution. CSRF is the largest per-request addition at 7.5 µs on a
state-changing request with a valid token (one HMAC); it does not run on
`GET`/`HEAD`/`OPTIONS`, which is the majority of editor traffic. `revokeAll`
scans all of a user's sessions by design.

**No baseline-vs-P5 comparison is claimed** for session *creation* or
*revocation*: the previous implementation had no equivalent operation to
measure — it could not revoke at all.

## 5. A real defect the benchmark caught (and fixed)

The first benchmark run showed `Session create` at **148 µs** and touching
validates at **11 µs** once the store reached capacity. Cause: `store.set()`
called a full `sweep()` over every session on **every** insert, making inserts
O(n) — and because a touch is also a `set`, the read path triggered it too.

Two bugs, both real:

1. **Hot-path latency:** at capacity, every authenticated request paid an O(n)
   sweep. A session flood therefore degraded request latency by ~160x.
2. **Correctness, worse:** a touch on the read path could evict a *different*
   user's live session. Ordinary traffic could destroy authority.

Fix: eviction now runs **only when a new key is inserted**, and reclaims with a
bounded scan (`evictScan: 32`, Map preserves insertion order) instead of a full
sweep.

| measured at capacity | before | after |
|---|---:|---:|
| touching validate | 11,000 ns | **1,300 ns** |
| session create | 141,000 ns | **9,700 ns** |
| live session survives touching validates | no | **yes** |

Both are now locked by regression tests (`a touching validate never evicts`,
`insertion stays bounded at capacity`).

## 6. Two integration defects found and fixed while wiring

- **`POST /rest/login` set only the session cookie, not the CSRF cookie.** Since
  the token is bound to the session id, every re-login left a stale CSRF cookie
  that failed against the new session. Surfaced as a 403 on the first
  post-login write.
- **Allowed origins were derived from `config.port`.** Under test (and behind a
  port-forwarding proxy) the server binds an ephemeral port, so the computed
  origin never matched. Now derived from the request's own `Host` header, which
  is what "same-origin" actually means.

## 7. Compatibility: the e2e harness now models a browser

Two e2e helpers (`rest.test.mjs`, `compat.contract.test.mjs`) were updated to
send `Origin` and echo the CSRF cookie into `x-n8n-csrf-token` — exactly what
the editor does, and what makes the double-submit check meaningful.

This is stated plainly because it could otherwise look like relaxing a test to
get green: **no server-side check was weakened.** The harness was corrected to
model reality; a browser has always sent `Origin` on state-changing requests.
The comment recording this sits above both helpers.

## 10. Known limitations

- The session store is **process-local and not persisted**. This is intentional:
  a session must not survive the process that is supposed to be able to kill it.
  Consequence: a restart signs everybody out, and the store is not shared across
  instances (multi-instance session consensus is explicitly non-scope).
- **No session list endpoint yet** — `sessionsForUser`/`inspectSession` exist but
  are not exposed over REST.
- **Rotation is on demand**, not automatic on privilege change. Wiring it into
  password change / MFA enablement is P5.6, which owns those mutations.
- **CSRF double-submit is enforced only once a token has been issued** (the
  cookie is present). A session-less or API client is governed by the origin
  check; proper machine identity arrives with API keys in P5.7.
- The idle-window touch rewrites the session record on each request, so
  authenticated traffic keeps sessions hot in the store.
