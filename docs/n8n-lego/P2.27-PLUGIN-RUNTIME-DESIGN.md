## 1. Core principle

> **Everything that is a meaningful system boundary should be replaceable as a
> Plugin/LEGO; the Core remains tiny, stable, and security-critical.**

What this does **not** mean:

```text
every function = plugin          ✗
every helper = plugin            ✗
every component = plugin         ✗
every service = microservice     ✗
```

The correct rule:

> **A plugin is an independently meaningful unit with contract, lifecycle,
> ownership, dependency, capability/security boundary, test boundary, and
> upgrade path.**

If a unit cannot name all seven, it is a module — not a plugin.

## 2. Core model

```text
                         N8N LEGO
                            │
                    ┌───────▼────────┐
                    │    LEGO CORE   │
                    │   tiny kernel  │
                    └───────┬────────┘
                            │
                  Contract / Capability
                            │
         ┌──────────────────┼──────────────────┐
         │                  │                  │
      in-process           WASM             process
         │                  │                  │
      trusted           sandboxed          isolated
         │                  │                  │
         └──────────────────┼──────────────────┘
                            │
                          remote
```

Core is responsible only for the minimum platform primitives required to run
plugins safely.

## 4. Plugin boundary

A plugin declares, at minimum:

```text
contract         the published interface it satisfies (id@version range)
lifecycle        how it is discovered, validated, started, health-checked,
                 drained, stopped, quarantined, upgraded, rolled back
ownership        who is accountable (manager vs assigned agent)
dependency       what it requires from Core and from other plugins
capability       requested capabilities + trust class + runtime class
test boundary    its own suite; Core's suite never imports plugin internals
upgrade path     side-by-side v1→v2 with validation, health, contract test
```

Plugin identity and plugin locality are separate concepts: changing
`Rust → Python` must not change the logical plugin contract.


## 6. Runtime classes and the locality rule

```text
in-process       trusted, small, hot-path, low-risk
wasm             portable computation, restricted/untrusted code
isolated-process Python, native plugins, high-risk implementations,
                 crash isolation, different runtime environments
remote           external providers, large workloads, independent
                 horizontal scaling, remote services
```

Locality rule:

```text
trusted + hot path                 → in-process
runtime mismatch / crash risk      → isolated process
untrusted compute                  → WASM/sandbox
external / independent scale       → remote
```

Performance principle:

```text
fine-grained / hot-path calls      → direct in-process
coarse-grained workload            → IPC/process
external service                   → remote
```

This exists specifically to prevent `Everything is Plugin → Everything becomes
microservice → performance collapses → RAM usage explodes`. Avoid
`Core → plugin A → Core → plugin B → Core` chains for tiny operations. Batch
where appropriate; reuse persistent workers; reuse external connections where
safe; never spawn a new process per request.

## 7. Language independence

> **Plugin implementation language is not part of consumer coupling.**

Allowed implementation languages:

```text
Rust · JavaScript · Python · WASM
```

provided the implementation satisfies the same canonical contract.

```text
ai.memory
   ├── memory-rust
   ├── memory-js
   └── memory-python
```

The consumer sees `ai.memory@1.x`, not the implementation language. Existing P2
migrations follow the same rule: Memory JS→Rust→Python, Execution JS→Rust, Node
runtime JS→Rust→WASM are **implementation migrations, not architectural
rewrites**.

## 8. Trust classes

```text
CORE       smallest possible trusted base
TRUSTED    audited internal plugins
ISOLATED   separate process + resource enforcement
SANDBOXED  untrusted / third-party / user / agent-generated code
```

Trust is an **explicit policy**, never a property of the programming language:
Rust is not automatically trusted; Python is not automatically unsafe.

## 9. Security principles (normative)

```text
deny-by-default
least privilege
explicit capability grant
no implicit authority
no authority inheritance
tenant-aware authorization
resource limits
credential isolation
plugin crash isolation
plugin quarantine
supply-chain verification
atomic upgrade
rollback
```

## 10. Capability security

Plugin manifest declares `capabilities.requested`. Core evaluates:

```text
requested capability → security policy → grant/deny
```

- A plugin cannot grant itself a capability.
- A plugin cannot silently acquire a capability through another plugin.

## 11. No authority inheritance

Reserved rule:

```text
grant(B) <= grant(A)      when A delegates to B
```

Mandatory for `plugin → plugin`, `agent → plugin`, `tenant → plugin`
delegation. Invoking another plugin never accidentally widens authority.

## 12. Secret broker

```text
plugin → secret broker → scoped short-lived secret → one operation
```

- `plugin → credential database` is forbidden.
- Secrets never become plugin-owned persistent state.
- LEGO never stores a standing credential (same discipline P2.25 established
  for provider adapters: handed over per call, never stored/logged/echoed).

## 13. Tenant security context

Reserved invocation context:

```text
tenantId
principalId
sessionId
requestId
correlationId
capabilityScope
resourceBudget
deadline
```

Every plugin operation stays tenant-scoped. Tenant A never reaches Tenant B by
calling another plugin. Tenant identity is never inferred from plugin
implementation state.

## 14. Resource security

Manifest declares intended limits; runtime enforces them. Documentation alone
is insufficient:

```text
cpu · memory · concurrency · queue depth · timeout · output size ·
network · filesystem · process count
```

## 15. Failure isolation — supervisor semantics

```text
DISCOVERED → VALIDATING → STARTING → HEALTHY → DEGRADED → DRAINING →
STOPPED → QUARANTINED
```

Crash behavior: `plugin crash → supervisor detects → restart/recover → health
check → healthy`. Repeated crash: `crash loop → quarantine` — never endlessly
restart a broken plugin. Core must remain alive when an isolated plugin dies.

## 16. Circuit breaker (external/remote plugins)

```text
CLOSED → OPEN → HALF-OPEN → CLOSED
```

Repeated provider failures must not consume unlimited Core resources.

## 17. Deadline propagation

```text
parent deadline → plugin deadline → child plugin deadline
```

A child cannot expand the parent deadline. Integrates with the existing Agent
Machine / runtime deadline model (P2.16/P2.21, P2.25 `deadline_exceeded`).

## 18. Contract replay

```text
production failure → contract-safe fixture → plugin v1 → plugin v2 →
compare semantic result
```

Goal:

```text
same input contract + same semantic contract = interchangeable implementation
```

This is what makes a language/runtime replacement safe.

## 19. Upgrade model (side-by-side)

```text
old v1 │ new v2 │ validate → health check → contract test → warm
        ↓ activate v2 → drain v1 → stop v1
failure: v2 unhealthy → rollback v1
```

No full application restart per plugin upgrade. Atomic upgrade + rollback are
normative (§9).

## 20. Debugging and operator model

Each plugin eventually has: `manifest · contract · implementation · tests ·
logs · metrics · health · diagnostics`. An operator identifies
`plugin · version · runtime class · contract · requestId · failure` without
inspecting the whole application.

Reserved operator surface (implementation may choose different CLI/API):

```text
lego plugin list
lego plugin inspect <id>
lego plugin health <id>
lego plugin logs <id>
lego plugin enable <id>
lego plugin disable <id>
lego plugin upgrade <id>
lego plugin rollback <id>
```

## 21. Supply-chain model

Admission flow:

```text
artifact
→ verify signature → verify digest → verify provenance
→ verify contract → verify requested capabilities → verify resource policy
→ health check → activate
```

An unverified plugin artifact is **never** executed automatically.

## 22. Frontend plugin model

```text
trusted frontend extension      → public extension points
untrusted / high-risk code      → sandboxed frame/origin + message contract
```

A frontend plugin never receives unrestricted application state merely
because it is a UI extension.

## 23. Scaling model

Remote/isolated plugins scale independently (stateless boundaries, request-
bound context, resource budgets). In-process plugins scale with the Core
process and stay on the hot path. Locality rule (§6) is what keeps independent
scaling from becoming default microservice sprawl.

## 24. What P2.27 is NOT

```text
microservice rewrite
Kubernetes migration
full distributed scheduler
full marketplace
complete third-party plugin ecosystem
rewrite of all P2 components
rewrite to Rust
rewrite to Python
```

P2.27 is the **plugin runtime/security foundation**. Existing P2 LEGO
implementations adapt gradually:

```text
P2 contract → plugin identity → plugin manifest → runtime adapter →
implementation
```

First as `in-process` plugins; selectively later to `WASM / process / remote`
**without changing the public contract**.
