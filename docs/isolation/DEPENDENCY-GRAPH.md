                             ▲

**Key correction vs. the example graph in the Agent-5 brief:** the brief sketched
`Workflow → Node → Graph` and a separate `Execution` root. In n8n 2.9.4 the
`workflow` package has **no** execution root — execution lives in `packages/core`
(out of Phase-2 scope). Inside `packages/workflow`, `workflow.ts` depends on
`expression` at runtime (it constructs `new Expression(this)`), which the example
graph did not show. The documented graph above is the source-verified one.

## 3. Direction notes per LEGO

* **workflow (Agent 1)** — fan-out hub. Runtime deps on `node`, `expression`, `interfaces`, shared utils. Nothing in `workflow.ts` imports persistence, HTTP, or DB. ✅ boundary clean.
* **node (Agent 2)** — depends on `validation` and `expression` at runtime; references `Workflow` **type-only**, so Node does not runtime-couple back to Workflow. ✅ good isolation seam.
* **connection (Agent 3)** — the cleanest LEGO: exactly one TYPE-ONLY edge to `interfaces`. Extractable today with zero runtime coupling.
* **validation (Agent 4)** — `workflow-validation.ts` is type-only against `interfaces`. Also very clean. Note it does *not* implement the cycle detection promised by `contracts/validation.contract.md` (see `CROSS-AGENT-ISSUES.md` ISSUE-003).
* **interfaces** — unowned shared hub with 40+ inbound edges. Highest-risk shared surface; needs an owner before Phase 3.

## 4. Optional / runtime / test-only

* `OPTIONAL`: none detected (no lazy `import()` across LEGO boundaries in `packages/workflow`).
